# График

## Зафиксированные архитектурные правила

- Общий UI/CSS является единым визуальным слоем.
- Не допускаются самовольные отдельные CSS-системы внутри отдельных веток.
- Если UI-компонент используется только одной веткой, это не означает, что его визуальная реализация должна дублироваться в этой ветке: общий UI-компонент остаётся общим, а принадлежность использования определяется веткой.
- Календарная сетка — один общий UI-компонент.
- Переключатель `Год → Месяц → День` — отдельный общий UI-компонент, используемый Графиком.
- Переключатель `Месяц → Год` — отдельный общий UI-компонент, используемый Журналом.
- Состояние и результат использования этих компонентов не являются общими: График и Журнал могут находиться на разных месяцах.
- Если в Графике календарная сетка или её состояние ошибочно связаны как единое состояние с другой веткой, это является ошибкой.
- Дополнительные настройки, относящиеся только к Графику, остаются принадлежностью Графика; их не следует превращать в глобальные настройки.

## UI

- Календарная сетка — общий UI.
- Управление рабочим периодом и формирование рабочего дня — ответственность Графика.
- Отображение рабочего дня в сетке — по состоянию, сформированному Графиком.
- Временной блок рабочего дня — специальное содержание Графика, использующее общий UI.
- Общие выпадающие/модальные элементы не дублируются внутри Графика.

## CSS

- Главный принцип: единый общий CSS.
- Специфические классы допустимы только как контекстные варианты общего визуального слоя, а не как отдельная визуальная система.

```text
Modal «Новый материал»
├── Название материала
│   └── [поле ввода]
│
├── Категория
│   ├── [ввод категории]
│   ├── список уже добавленных категорий
│   └── [+ добавить категорию]
│
├── Подкатегория
│   ├── [ввод подкатегории]
│   ├── список уже добавленных подкатегорий
│   └── [+ добавить подкатегорию]
│
├── [Сохранить]
└── [×]
```

### Формирование категорий и подкатегорий

- Список категорий не является жёстко зашитым в коде.
- Пользователь постепенно создаёт собственный список категорий.
- После добавления категории она появляется в текущем списке, при этом остаётся возможность добавить следующую.
- Аналогично пользователь постепенно создаёт список подкатегорий.
- Подкатегория является дополнительным уровнем фильтрации и может использоваться или не использоваться.
- Первоначальное состояние выбора может быть пустым с понятным назначением поля.
- Созданные пользователем `Тип` и `Подтип` также должны формироваться через общий UI выпадающих списков и не должны быть жёстко зашиты в коде.
- Эти уровни классификации используются позднее при формировании состава рецепта.

### Тип и Подтип

Целевая классификация материалов имеет два уровня:

```text
Тип
└── Подтип
```

В UI выбора существующих значений пользователь может выбрать значение из списка или добавить новое значение. Например, пользователь может создать `Краситель` как Тип и `Гель` как Подтип. Другой специалист может сформировать совершенно другую классификацию, соответствующую его работе.

Комбинация `Тип + Подтип` затем используется как фильтр при выборе материалов в рецепте.

### Целевая структура ветки

```text
Материалы
├── [Добавить материал]
├── список материалов
│   └── материал → [Удалить]
└── [Назад]
```

- `Добавить материал` — общий UI Action.
- Список материалов — общий UI списка с данными сущностей Материалов.
- `Удалить` — общий UI Action удаления, применённый к сущности Материал.
- `Назад` — общий UI Action «шаг назад», возвращает в `Рабочие материалы`.

### Ошибка текущей реализации

- 🔴 Текущая реализация Материалов неполна: она не соответствует целевой модели, в которой пользователь формирует категории/подкатегории и двухуровневую классификацию через общий UI.
- 🔴 Нельзя рассматривать Материалы как простую копию Товаров: общий только UI-механизм, а данные и логика сущности Материал собственные.

# Настройки → Рабочие материалы → Рецепты

## Архитектура и владение

```text
Рабочие материалы
└── Рецепты
    └── единственный владелец сущности «Рецепт»
```

- Ветка `Рецепты` владеет конечной сущностью `Рецепт`.
- `Рабочие материалы` владеют родительской веткой `Рецепты`, но не конечной сущностью.
- Сущность Рецепт создаётся внутри ветки `Рецепты`.

## UI первого уровня

```text
Рецепты
├── пусто, если рецептов ещё нет
├── [Добавить рецепт]
├── после создания → список рецептов
└── [Назад]
```

- Пустое состояние — корректное состояние до создания первого рецепта.
- `Добавить рецепт` — общий UI Action создания сущности.
- После сохранения созданная сущность появляется в списке рецептов.
- `Назад` — общий UI Action «шаг назад», возвращает в `Рабочие материалы`.

## Modal «Новый рецепт»

Используется общий Modal UI. Внутри него находятся общие UI-компоненты ввода и выбора, но данные относятся к сущности Рецепт.

```text
Новый рецепт
│
├── Наименование
│   └── [поле ввода]
│
├── Определение
│   └── [поле ввода]
│
├── Состав
│   ├── Категория
│   │   └── [выпадающий список]
│   ├── Тип
│   │   └── [выпадающий список]
│   └── Материал
│       └── [выпадающий список]
│           └── материалы фильтруются по классификации
│
├── [+ Материал]
├── [Сохранить рецепт]
└── [×]
```

### Данные рецепта

- `Наименование` — название рецепта, вводится в отдельное поле.
- `Определение` — отдельное ручное уточнение того, что именно делаем/красим: например, корни, длину и т. п. Это не второе название рецепта.
- `Состав` — заголовок группы UI, внутри которой выбираются параметры состава.
- `Категория` — выпадающий список классификации материалов.
- `Тип` — выпадающий список второго уровня классификации.
- `Материал` — выпадающий список доступных материалов с фильтрацией по выбранной классификации.
- `+ Материал` — добавляет ещё один элемент состава внутри того же Modal. Это дополнительный UI внутри общего Modal, а не новый Modal.
- Количество добавленных материалов не ограничивается одним элементом в рамках описанной логики.
- `Сохранить рецепт` — сохраняет сущность Рецепт.
- `×` — закрывает Modal.
- Кнопки `Назад` внутри Modal нет.

## Связь с Материалами

- Рецепт использует классификацию, сформированную в Материалах.
- Пользователь может создавать собственные `Тип` и `Подтип`, например `Краситель → Гель`, или совершенно другую классификацию для другого вида работы.
- При выборе материала в составе рецепт использует соответствующий фильтр классификации.
- Это не создаёт нового владельца сущности Материал: владельцем остаётся `materials.js`.

## После сохранения

```text
Рецепты
└── Список рецептов
    └── созданный рецепт
```

- Сохранённый рецепт появляется в списке Рецептов.
- Дальнейшие правила хранения и истории данных пока не проектируются.

# Общие правила UI / Modal

## Modal

Modal — один общий UI-механизм CoBook.

- Не создаётся отдельный Modal для Процедур, Товаров, Материалов, выбора времени, перерыва и других сценариев.
- Один общий Modal используется с разным содержимым.
- Общий CSS.
- Общее позиционирование.
- Всегда привязка к центру экрана.
- Любое устойчивое смещение Modal вниз/вверх/влево/вправо считается ошибкой общего UI/CSS.
- `×` — общий UI Action закрытия.
- `Сохранить` — общий UI Action сохранения данных сценария.
- В Modal нет кнопки `Назад`: навигационное `Назад` предназначено для перехода между экранами/ветками, а не для закрытия Modal.
- Внутри Modal могут использоваться дополнительные UI-компоненты: выпадающие списки, переключатели, барабаны выбора времени, дополнительные поля и другие вложенные UI.
- Дополнительный UI внутри Modal не превращает Modal в отдельный/локальный компонент.
- Один и тот же Modal может иметь разный набор полей и действий в зависимости от сущности, но базовый механизм Modal остаётся общим.

## Общий UI и CSS

- UI-компонент остаётся общим независимо от того, в какой ветке и с какими данными он используется.
- Разные данные или дополнительные вложенные UI не являются основанием для создания отдельной UI-функции.
- Общий CSS является единым визуальным слоем.
- Локальные CSS/renderer допустимы только как контекстное использование общего визуального слоя, а не как отдельная визуальная система.

# Правило продолжения

После каждой закрытой ветки результат добавляется в накопительную структуру, а не используется для переписывания уже утверждённых веток.

Следующая ветка для разбора: продолжение внутри `Настройки → Рабочие материалы → Рецепты` только при появлении новых вопросов; уже утверждённые уровни не пересматриваются без новой причины.

Финальная цель: собрать из накопленных веток один целостный файл Mind Map CoBook, а не набор независимых документов.
