### Функциональные действия в коде

В `app/maine/maine.js`:

```text
clients-open  → открыть Клиенты
client-new    → создать нового клиента
client-open   → открыть карточку клиента
client-save   → сохранить клиента
client-back   → вернуться из карточки в список
maine-back    → вернуться из Клиентов в Главную
```

### Архитектурный статус

- 🔴 `clients-open`, `client-new`, `client-open`, `client-save`, `client-back`, `maine-back` зарегистрированы в Core с владельцем `maine`.
- 🔴 Это зафиксировано как архитектурная проблема для внутреннего функционала Клиентов: действия Клиентов сейчас маршрутизируются владельцу `maine`.
- 📌 Целевой принцип: Main передаёт управление ветке Клиенты; внутренние действия Клиентов принадлежат Клиентам.

В `actionOwners` текущий код содержит:


Следовательно, внутренние действия Клиентов фактически обслуживаются модулем `maine`.

### Статус

🔴 Архитектурная ошибка зафиксирована.

### Целевой принцип

```text

Main
 ↓

 ↓
функционал Clients
```

Core предоставляет механизм маршрутизации и общие возможности. Core не должен забирать себе предметный функционал Клиентов.

# 16. ГРАФИК — ЭКРАН

Статус: 🟡 ветка находится в работе.

Экран Графика рассматривается сначала только как экран: что пользователь видит и какие UI-части в нём существуют. Функциональные и архитектурные выводы фиксируются отдельными разделами.

## Структура экрана

Экран состоит из трёх блоков:

```text
📁 График
│
├── Блок заголовка
├── Блок календаря
└── Блок временного диапазона
```

### Блок календаря

Зафиксировано по текущему разбору:

- 🔴 Сейчас переключение года и месяца реализовано двумя отдельными бегунками.
- 📌 Целевое состояние — один общий переключатель периода: год + месяц как единое состояние, например `2026 · Июнь`.
- 🔴 В сетке отображаются даты предыдущего месяца, но даты следующего месяца в конце сетки сейчас не отображаются полностью.
- 📌 Сетка должна рассчитываться динамически так, чтобы отображались необходимые даты соседнего месяца до заполнения календарной области.
- 🔴 Текущая сетка визуально воспринимается как набор маленьких кнопок.
- 📌 Целевой UI — полноценная календарная сетка, рассчитанная на размещение дополнительной информации внутри ячейки, а не просто кнопочная ячейка.

### Блок временного диапазона

- 🟢 Визуально блок является отдельным временным блоком.
- ⚠️ Функциональная проверка временного блока на этом этапе не завершена.

# 17. ГРАФИК — CORE И ВЛАДЕНИЕ СУЩНОСТЬЮ «РАБОЧИЙ ДЕНЬ»

## Зафиксированный архитектурный принцип

```text
Core
  ↓ передаёт действие / запрос
График
  ↓ владеет
Рабочий день
```

`Рабочий день` — сущность Графика.

Она формируется из двух составляющих:

```text
День + Временной диапазон
        ↓
   Рабочий день
```

### Что запрещено

```text
❌ Main владеет Рабочим днём
❌ Journal владеет Рабочим днём
❌ Core напрямую создаёт/изменяет Рабочий день
❌ Journal создаёт отдельную копию Рабочего дня
```

### Правильное взаимодействие Журнала с Графиком

Журнал может запрашивать у Графика действие над сущностью, но не становится её владельцем.

Пример:

```text
Журнал
  ↓ запрос
График
  ↓ изменяет свою сущность
Рабочий день
```

Если Журналу требуется изменить время, это является запросом к Графику на изменение принадлежащего Графику Рабочего дня.

Если Журнал показывает время Рабочего дня, он получает данные от Графика. Это отображение не означает владение сущностью.

### Статус

🔴 В текущей архитектуре ранее обнаружено несоответствие: право владения Рабочим днём было распределено не только Графику. Это должно быть исправлено так, чтобы единственным владельцем сущности оставался График.

📌 Core отвечает за передачу действия/запроса. График отвечает за предметную сущность.

# 18. ГРАФИК — ОБЩИЙ UI: РАЗДЕЛЕНИЕ РЕВЕРСНЫХ И КАЛЕНДАРНЫХ КОМПОНЕНТОВ

Важно не объединять разные UI-компоненты в один «универсальный Reverse UI».

## 18.1 Reverse Action Button

Общий UI-компонент.

Смысл:

```text
состояние A
   ↕
состояние B
```

Компонент имеет единый визуальный механизм переключения состояний. Конкретный модуль передаёт смысл состояний и тексты.

В Графике пример:

```text
Применить рабочий день
        ↕
Применить выходной день
```

График использует компонент, но не владеет самим UI-компонентом.

📌 Если тот же Reverse Action Button используется в другом разделе, его базовый визуал должен оставаться общим.

## 18.2 Reverse Date Selection

Это отдельный UI-компонент/паттерн, не являющийся кнопкой.

Он отвечает за реверсивный режим выбора дат в календарной сетке.

```text
режим выбора рабочих дат
→ выбранная дата: бежевый фон + чёрный текст

режим выбора выходных дат
→ выбранная дата: коричневый фон + белый текст
```

Это визуал именно **выбора**, а не постоянного статуса даты.

### Правило группового выбора

После первой выбранной даты фиксируется направление операции:

```text
первая дата — нерабочая
→ выбираем только нерабочие даты
→ рабочие даты недоступны для добавления в эту группу

первая дата — рабочая
→ выбираем только рабочие даты
→ нерабочие даты недоступны для добавления в эту группу
```

Нельзя смешивать рабочие и нерабочие даты в одной операции, потому что это создаёт конфликт двух противоположных действий.

Это правило относится к функционалу Графика, а визуальное состояние выбранной ячейки относится к UI-компоненту выбора.

# 19. ГРАФИК — CALENDAR GRID КАК ОБЩИЙ UI

`Calendar Grid` — общий UI-компонент, используемый календарями разных разделов, в том числе Графиком и Журналом.

Он не принадлежит Графику и не принадлежит Журналу.

```text
UI CORE
└── Calendar Grid
      │
      ├── График использует
      └── Журнал использует
```

## Что является общим знанием UI

Calendar Grid знает универсальные правила отображения календаря:

```text
текущий выбранный месяц
предыдущий месяц
следующий месяц
суббота / воскресенье
рабочий день
выходной день
выбранная дата
```

### Визуальные правила

```text
Дата текущего месяца
→ стандартный вид

Дата предыдущего / следующего месяца
→ светло-серый цвет + меньший шрифт

Суббота / воскресенье
→ красное отображение

Рабочий день
→ жирный шрифт

Выходной день
→ обычный шрифт
```

Важно: `выходной день` здесь означает статус рабочего графика, а не субботу или воскресенье.

### Выбор и статус — разные понятия

```text
СТАТУС ДАТЫ
→ рабочий / выходной
→ влияет на визуал самой даты

ВЫБОР ДАТЫ
→ пользователь выбрал дату для операции
→ может давать заливку выбранной ячейке
```

Заливка бежевым/коричневым относится к **выбору**, а не к постоянному статусу «рабочий/выходной».

Сам факт, что день является рабочим, не должен превращать ячейку в залитую кнопку.

### Владение данными и отображение

```text
График
  └── владеет сущностью Рабочий день
          │
          │ передаёт состояние
          ▼
UI Core / Calendar Grid
          │
          └── отображает состояние по общим правилам
```

UI знает **как отображать** состояние, но не владеет сущностью.

То же правило действует для Журнала: если Журнал получает от Графика состояние Рабочего дня, он использует тот же общий Calendar Grid и те же правила отображения.

### Архитектурное правило

> **Владение сущностью и визуальное отображение её состояния — разные ответственности.**

Владелец сущности сообщает состояние. Общий UI применяет единое правило отображения.

# 20. ГРАФИК — ТЕКУЩАЯ ТОЧКА

На данный момент по Графику зафиксировано:

```text
ЭКРАН
├── 🟡 Заголовок
├── 🔴 Календарь
│   ├── 🔴 два бегунка «год» + «месяц»
│   ├── 🔴 нет полного хвоста дат следующего месяца
│   └── 🔴 сетка слишком похожа на набор кнопок
└── 🟢 Временной диапазон — визуально

CORE
└── 🔴 владение Рабочим днём требует исправления

UI
├── 🟢 Reverse Action Button — отдельный общий компонент
├── 🟢 Reverse Date Selection — отдельный компонент/паттерн
├── 🟢 Calendar Grid — общий UI для календарей
└── 🟢 Date State Display — часть общего Calendar Grid, не отдельное действие
```

Следующий шаг: продолжать разбор **оставшихся UI-компонентов Графика**, не возвращаясь к уже закрытому Core, если не обнаружится новое противоречие в коде.

После каждого завершённого смыслового блока его результат обязан быть внесён в этот документ до перехода к следующему блоку.

Минимально фиксируются:

```text
что существует;
что сейчас работает;
что сейчас не работает;
что работает, но архитектурно неправильно;
кто владеет сущностью;
кто только использует сущность;
какой UI общий;
какой UI является специальным;
какие правила являются общими;
какой CSS должен быть общим;
что должно быть исправлено.
```

Нельзя считать обсуждение завершённым, если вывод остался только в чате и не перенесён в PRE-MIND MAP.
