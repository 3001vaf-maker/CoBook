# CoBook — PRE-MIND MAP

## Назначение

Рабочий документ непрерывности проекта CoBook.

Цель: последовательно разобрать фактическую архитектуру проекта по веткам и зафиксировать:
- экран;
- структуру папок/веток;
- функционал;
- владельца функционала;
- Core / передачу действий;
- UI-компоненты;
- CSS / визуальный слой;
- что реально работает;
- что реально не работает;
- архитектурные ошибки;
- что должно быть после исправления.

Этот документ ведётся вместе с кодом проекта и является промежуточной основой будущего Mind Map.

---

# 1. ОБЩАЯ СТРУКТУРА CoBook

Фактическое нижнее меню из `app/shared/core.js`:

```text
CoBook
│
├── Главная        (maine)
├── График         (timetable)

```

Правило разбора: будущие ветки не придумываются. Добавляются только существующие в коде.

---

# 2. АРХИТЕКТУРНОЕ ПРАВИЛО ВЕТОК

```text
Core
  ↓
Главная
  ↓
Клиенты
  ↓
внутренний функционал Клиентов
```

Владелец функционала должен соответствовать ветке, которой этот функционал принадлежит.

Главная является родительской веткой Клиентов, но не должна владеть внутренним функционалом Клиентов.

# 4. ГЛАВНАЯ → КЛИЕНТЫ

## Экран

```text
📁 Клиенты
│
├── 📋 Список клиентов
│
├── 🔘 Добавить клиента
│
└── 🔘 Назад
```

### Текущее состояние по факту работы

- 🟢 Список клиентов отображается.
- 🟢 Клиента можно открыть нажатием на элемент списка.
- 🟢 Функционал добавления клиента существует.
- 🟢 Кнопка «Добавить клиента» работает.
- 🟠 Кнопка «Добавить клиента» сейчас находится снизу; целевое положение — сверху.
- ⚠️ Пользователь наблюдает, что «Назад» перемещается вместе с экраном/списком. Требуется отдельная проверка фактического поведения текущей версии.

### Функциональные действия в коде

В `app/maine/maine.js`:

```text
clients-open  → открыть Клиенты
client-new    → создать нового клиента
client-open   → открыть карточку клиента
client-save   → сохранить клиента
client-back   → вернуться из карточки в список
maine-back    → вернуться из Клиентов в Главную
```

### Архитектурный статус

- 🔴 `clients-open`, `client-new`, `client-open`, `client-save`, `client-back`, `maine-back` зарегистрированы в Core с владельцем `maine`.
- 🔴 Это зафиксировано как архитектурная проблема для внутреннего функционала Клиентов: действия Клиентов сейчас маршрутизируются владельцу `maine`.
- 📌 Целевой принцип: Main передаёт управление ветке Клиенты; внутренние действия Клиентов принадлежат Клиентам.

# 5. КЛИЕНТЫ → ДОБАВИТЬ КЛИЕНТА

## Экран

```text
📁 Клиенты
└── ➕ Добавить клиента
    │
    ├── 📋 Блоки данных
    ├── 🔘 Сохранить
    └── 🔘 Назад
```

### Текущее состояние

- 🟢 Блоки данных отображаются.
- 🟢 Новый клиент создаётся.
- 🟢 Новый клиент сохраняется в `localStorage`.
- 🟢 «Назад» работает.
- 🔴 После сохранения пользователь не попадает автоматически в список клиентов.
- 🟢 При ручном переходе назад список отображается.

### Важное уточнение

Проблема «Сохранить» — не в самом создании/сохранении клиента.
Проблема относится к результату после сохранения и переходу/рендеру списка.

Целевое поведение:

```text
Сохранить
   ↓
клиент сохранён
   ↓
список клиентов автоматически отображён
```

Внутренние поля и блоки данных здесь пока не разбираются. Это отдельный этап после архитектурного разбора.

# 7. CORE — ТЕКУЩЕЕ СОСТОЯНИЕ

Файл: `app/shared/core.js`.

Core содержит:

```text
Общее состояние
Хранилище localStorage
Навигацию
Глобальный render()
Маршрутизацию data-action
Реестр владельцев действий
Общие UI-фабрики
```

## Передача действий

Фактическая цепочка:

```text
UI
 ↓
data-action
 ↓
Core dispatchAction()
 ↓
actionOwners
 ↓
module.handle()
 ↓
state / localStorage
 ↓
window.render()
```

## Обнаруженная проблема Клиентов

В `actionOwners` текущий код содержит:

```text
clients-open  → maine
client-new    → maine
client-open   → maine
client-save   → maine
client-back   → maine
maine-back    → maine
```

Следовательно, внутренние действия Клиентов фактически обслуживаются модулем `maine`.

### Статус

🔴 Архитектурная ошибка зафиксирована.

### Целевой принцип

```text
Core
 ↓
Main
 ↓
Clients
 ↓
функционал Clients
```

Core предоставляет механизм маршрутизации и общие возможности. Core не должен забирать себе предметный функционал Клиентов.

# 8. UI — КАНОНИЧЕСКИЕ КОМПОНЕНТЫ

Полный зарегистрированный набор:

| UI | Перевод | Назначение |
|---|---|---|
| BUTTON | кнопка | стандартное действие |

| SELECT | поле выбора | выбор одного значения из списка |
| TEXTAREA | многострочное текстовое поле | ввод большого текста |
| FILE_FIELD | поле выбора файла | выбор файла |
| MODAL | модальное окно | всплывающее окно поверх экрана |
| BOTTOM_SHEET | нижняя выезжающая панель | панель, появляющаяся снизу |
| DROPDOWN | выпадающее меню | меню со списком вариантов |

### Важное правило

Наличие общей UI-фабрики само по себе не доказывает, что весь проект её использует. Фактическое использование каждого компонента проверяется по коду.
