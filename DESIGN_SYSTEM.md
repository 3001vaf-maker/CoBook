# CoBook — DESIGN SYSTEM

## Назначение

Этот документ является источником правил для всех задач, связанных с внешним видом интерфейса CoBook.

`PROJECT_STATE.md` определяет общую архитектуру проекта и обязательный протокол проверки. Этот документ конкретизирует правила визуального слоя.

---

## 1. ЕДИНЫЙ CSS

Во всём CoBook используется один и только один CSS-файл:

```text
styles.css
```

Все визуальные изменения выполняются в рамках этого файла.

Запрещено создавать CSS внутри владельца MODULE или отдельной функциональной папки:

```text
journal.css      ❌
timetable.css    ❌
service.css      ❌
clients.css      ❌
loyalty.css      ❌
products.css     ❌
```

Папка MODULE отвечает за свою функциональность и данные. Она не владеет отдельным CSS.

---

## 2. ОБЛАСТЬ РАБОТЫ ≠ МЕСТО ДЛЯ CSS

Когда заказчик говорит:

```text
SETTINGS → SERVICE → Услуги → Прайс
```

или:

```text
Журнал → Календарь
График → Календарь
```

это означает **область интерфейса, которую нужно изменить**.

Это НЕ означает, что CSS нужно создавать внутри этой папки.

Правильно:

```text
app/
└── нужный MODULE

styles.css
└── визуальные правила нужного компонента
```

Перед изменением необходимо точно определить:

```text
Где находится визуальный элемент?
Какой именно компонент изменяется?
Какой MODULE является его владельцем?
Какие другие экраны используют этот компонент?
```

---

## 3. ОБЩИЕ КОМПОНЕНТЫ И ВАРИАНТЫ

Один CSS не означает, что абсолютно все элементы должны выглядеть одинаково.

Нужно разделять:

```text
ОБЩАЯ ОСНОВА
      ↓
ВАРИАНТ КОМПОНЕНТА
      ↓
КОНКРЕТНЫЙ ЭКРАН
```

Например, список может иметь одну общую основу, но разные функциональные варианты:

```text
LIST
├── обычный информационный список
├── список-кнопки
└── список-карточки
```

Это всё остаётся в `styles.css`.

Не создавать отдельные CSS для каждого варианта.

---

## 4. LIST

`LIST` — это визуальная система для перечней.

Сам факт наличия разных классов списка не является архитектурной ошибкой. Ошибка возникает, если каждый список получает полностью независимую систему дизайна без общей основы.

Принцип:

```text
Общий LIST
│
├── общая геометрия
├── общие отступы
├── общая типографика
├── общие границы/разделители
├── общие состояния
│
└── варианты
    ├── LIST + BUTTON       → например Прайс
    ├── LIST + CARD         → например Товары
    └── LIST + CARD         → например Лояльность
```

Поэтому Прайс, Товары, Лояльность и Клиенты могут отличаться по назначению и взаимодействию, но должны использовать единую визуальную систему.

---

## 5. CARD

Карточка — отдельный тип компонента.

Карточки разных сущностей могут иметь разное содержимое и разные информационные поля. Это нормально.

Но базовые принципы дизайна карточек должны находиться в общем `styles.css`.

Не создавать `client-card.css`, `product-card.css`, `loyalty-card.css` и подобные файлы.

Если конкретной карточке нужен уникальный визуальный вариант, он добавляется как класс/модификатор в общий `styles.css`.

---

## 6. BUTTON

Кнопки используют общую систему кнопок из `styles.css`.

Не создавать отдельные CSS-файлы для кнопок конкретного MODULE.

Если функционально разные кнопки требуют разных вариантов, они должны быть вариантами общей системы:

```text
BUTTON
├── основной
├── вторичный
├── действие
├── опасное действие
└── специальный вариант
```

### MAINE / Premium

`Premium` — специальный визуальный вариант кнопок Главной.

Он находится в общем `styles.css` и не является отдельным CSS или отдельной системой дизайна.

---

## 7. CALENDAR

В CoBook могут существовать разные календари с разной логикой.

Например:

```text
Журнал
└── календарь
    └── своя логика выбора

График
└── календарь
    └── своя логика выбора смен/рабочих дней
```

Их поведение определяется соответствующим JS/MODULE.

Но визуальный каркас календаря должен быть общим:

```text
CALENDAR
├── общая сетка
├── размеры
├── ячейки
├── дни недели
├── типографика
├── отступы
└── базовые состояния
```

Специфические состояния оформляются модификаторами внутри того же `styles.css`:

```text
calendar--journal
calendar--timetable
```

Изменение общей геометрии календаря должно затронуть оба календаря предсказуемо.

Изменение состояния, относящегося только к одному календарю, не должно менять другой.

Нельзя создавать:

```text
journal-calendar.css   ❌
timetable-calendar.css ❌
```

---

## 8. JS И CSS НЕ СМЕШИВАТЬ

JS отвечает за:

```text
что происходит
какое состояние
какое действие
что выбрано
куда перейти
```

CSS отвечает за:

```text
как это выглядит
размер
позиция
отступ
типографика
состояние отображения
```

Например:

```text
График JS
  ↓
выбрана смена
  ↓
state
  ↓
класс состояния
  ↓
styles.css
  ↓
визуальное отображение смены
```

Не создавать JS только ради визуального оформления, если это уже решается CSS.

Не создавать CSS только внутри MODULE, чтобы скрыть архитектурную проблему.

---

## 9. КТО ВЛАДЕЕТ ИЗМЕНЕНИЕМ

Перед визуальным изменением необходимо определить владельца.

Пример:

```text
SETTINGS → SERVICE → Прайс
```

Владелец функциональности — SERVICE.

Но источник визуального оформления — `styles.css`.

Другой пример:

```text
Журнал → календарь
```

Владелец поведения — Журнал.

Общий визуальный каркас календаря — `styles.css`.

Другой вариант:

```text
График → календарь → выбранная смена
```

Логика состояния — График.

Визуальный вариант состояния — `styles.css`.

---

## 10. ЗАПРЕТ НА НЕОЖИДАННЫЕ ПОБОЧНЫЕ ИЗМЕНЕНИЯ

Если заказчик просит изменить один конкретный компонент, нельзя автоматически менять другой компонент только потому, что они используют похожие классы.

Перед изменением общего CSS необходимо определить область влияния правила.

Если изменение общего класса затронет несколько экранов, это нужно установить до изменения.

Алгоритм:

```text
Запрос заказчика
      ↓
точный экран
      ↓
точный компонент
      ↓
его CSS-класс
      ↓
кто ещё использует этот класс?
      ↓
общий класс или локальный вариант?
      ↓
изменение
      ↓
проверка всех затронутых экранов
```

Если непонятно, должен ли визуальный эффект быть общим или локальным, **не делать предположение**. Сначала уточнить у заказчика.

---

## 11. ЯЗЫК ЗАКАЗЧИКА

Когда заказчик называет путь:

```text
папка → экран → кнопка
```

это следует понимать как указание **области работы**.

Например:

```text
SERVICE → Прайс → кнопки услуг
```

означает:

> работать с кнопками услуг в Прайсе.

Это не означает:

> создать `service.css` или CSS внутри папки SERVICE.

Если нужен новый визуальный компонент, он проектируется в рамках общей дизайн-системы и фиксируется в `styles.css`.

---

## 12. ПРОВЕРКА ПОСЛЕ ИЗМЕНЕНИЯ ДИЗАЙНА

После изменения необходимо проверить:

1. Сам экран, который был указан заказчиком.
2. Все другие экраны, использующие тот же общий компонент.
3. Состояния компонента: обычное, выбранное, активное, disabled и т. п., если они существуют.
4. Desktop.
5. Mobile.
6. Отсутствие появления нового CSS-файла внутри MODULE.
7. Отсутствие дублирования CSS.
8. Отсутствие неожиданных изменений в других владельцах.

Особенно важно для общих компонентов:

```text
изменили общий CSS
      ↓
проверить ВСЕ владельцы компонента
```

---

## 13. ПРАВИЛО ДЛЯ НОВОГО КОМПОНЕНТА

Перед созданием нового визуального компонента задать:

```text
1. Такой компонент уже существует?
2. Можно ли использовать существующий общий компонент?
3. Нужен новый вариант существующего компонента?
4. Действительно ли нужен новый класс?
5. Не создаёт ли это дублирование?
```

Если новый класс нужен — добавить его в `styles.css`.

Если нужен новый вариант — оформить его как вариант существующего компонента.

Если нужен полностью новый компонент — описать его в общем `styles.css` и зафиксировать назначение в этом документе при необходимости.

---

## 14. КЛЮЧЕВОЕ ПРАВИЛО

```text
ПАПКА       → владеет функциональностью и данными
JS          → отвечает за поведение и действия
CORE        → отвечает за центральную обработку
styles.css  → отвечает за визуальный язык
```

Путь, который называет заказчик, определяет **где он хочет видеть результат**, а не где нужно создавать CSS.

Никакая папка MODULE не получает собственный CSS только потому, что в ней появилась новая функция.

Если изменение затрагивает общий компонент — это должно быть осознанно проверено на всех его владельцах.

Если область влияния непонятна — сначала уточнить у заказчика, затем изменять.
