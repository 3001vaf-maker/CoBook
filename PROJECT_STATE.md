# CoBook — PROJECT STATE

## 1. Источник истины

`main` — текущая рабочая и контрольная точка проекта.

Перед каждой рабочей задачей необходимо прочитать актуальный `PROJECT_STATE.md` из `main`, затем проверить фактический код и только после этого вносить изменения.

Нельзя восстанавливать старую архитектуру по памяти или создавать новые файлы «на всякий случай».

## 2. БАЗОВАЯ АРХИТЕКТУРА

## 3. ОДИН ЦЕНТРАЛЬНЫЙ CORE

`app/shared/core.js` — единый технический механизм приложения.

Он отвечает за:
- состояние приложения;
- переходы между верхнеуровневыми экранами;
- нижнюю навигацию;
- единый механизм `render`;
- единый приём пользовательских действий;
- маршрутизацию `data-action`;
- общие технические утилиты.

### Нажатие кнопки

```text
Кнопка
  ↓
data-action
  ↓
core.js
  ↓
центральная обработка действия
  ↓
владелец нужного MODULE
```

MODULE не создаёт собственный глобальный обработчик `click`, если действие может быть обработано центральным `core.js`.

Запрещены обходы центральной системы:
- отдельные глобальные `onclick` для обхода Core;
- DOM-перехваты ради исправления архитектурной ошибки;
- временные `window.*`-мосты;
- дополнительные router/navigation fix-файлы;
- дублирование одного действия в нескольких местах.

## 4. ЕДИНЫЙ RENDER

Механизм рендера — **единый**.

`core.js` определяет текущий экран и запускает его отображение.

```text
core.js
   ↓
единый render-механизм
   ↓
владелец текущего экрана
   ↓
разметка этого экрана
```

Наличие `render()` внутри MODULE не означает наличие отдельного render-механизма.

`journal.js`, `maine.js`, `settings.js` и другие владельцы могут описывать содержимое своего экрана, но не создают собственный глобальный renderer.

Запрещено иметь несколько независимых механизмов рендера одного приложения.

## 5. ЕДИНЫЙ ВИЗУАЛЬНЫЙ СТИЛЬ

Весь визуальный стиль CoBook находится только в:

```text
styles.css
```

Это единственный CSS-файл приложения.

Правила:
- никаких `clients.css`, `finance.css`, `maine.css`, `settings.css`, `profile.css`, `service.css` и подобных локальных CSS;
- никакого CSS внутри папок MODULE;
- никакого отдельного CSS для кнопки или папки;
- новый визуальный компонент добавляется в общий `styles.css`;
- существующие UI-классы переиспользуются, а не копируются.

### MAINE / Premium

В общем `styles.css` существует специальный вариант кнопок Главной:

```text
.premium-grid
.premium
```

`Premium` — не отдельный CSS и не отдельный MODULE. Это дополнительный визуальный вариант кнопок `MAINE`, реализованный в общем `styles.css`.

```text
styles.css
├── общий UI
└── Premium
    └── специальный вариант кнопок MAINE
```

## 6. РОЛИ ФАЙЛОВ

`index.html` — оболочка приложения и подключение ресурсов.

`app.js` — только запуск приложения. Бизнес-логика MODULE в `app.js` запрещена.

`styles.css` — единый внешний вид всего приложения.

`core.js` — единая техническая обработка: state, navigation, actions и render-механизм.

`MODULE/*.js` — содержимое и логика конкретного владельца экрана.

MODULE не дублирует Core и не создаёт собственные глобальные механизмы навигации, кликов или рендера.

## 7. КОГДА НУЖЕН JS ВНУТРИ ПАПКИ

JS не является обязательным атрибутом каждой папки.

Он нужен только если папка содержит собственную логику: состояние, данные, форму, сохранение, динамическое содержимое, внутреннее переключение или действия, принадлежащие этому владельцу.

Простая папка/сущность, полностью описываемая родителем через общий механизм, не получает отдельный JS только ради наличия файла.

Поэтому `clients.js` нельзя создавать автоматически только потому, что существует папка `clients`.

## 8. SETTINGS

```text
SETTINGS
├── PROFILE
├── SERVICE
├── DOCUMENTS
├── LOYALTY
├── TAGS
└── WALLETS
```

`settings.js` существует потому, что `SETTINGS` является владельцем своего экрана и его внутренней структуры. Он не является отдельным обработчиком кликов: действия проходят через `core.js`.

Вложенные MODULE получают собственный JS только там, где действительно существует собственная логика владельца.

```text
SETTINGS
└── SERVICE
    ├── ПРОЦЕДУРЫ
    └── ТОВАРЫ
```

Физически:

```text
app/settings/service/

│   └── procedures.js
```

`service.js` владеет окном SERVICE и его внутренним состоянием.

`procedures.js` и `products.js` — внутренние части SERVICE и не становятся верхнеуровневыми MODULE.

## 10. PROFILE

```text
SETTINGS
└── PROFILE
```

Физически:

```text
app/settings/profile/profile.js
```

`profile.js` владеет содержимым, формами и сохранением профиля.

Не создавать `app/profile/`.

## 11. MAINE

`MAINE` — Главная мастера.

```text
MAINE
├── Клиенты
└── Финансы
```

Клиенты и Финансы — внутренняя функциональность Main, а не верхнеуровневые MODULE.

Физическое правило для Клиентов:

```text
app/maine/
└── clients/
```

`app/clients/` запрещён.

`CoBook.modules.clients` запрещён.

`state.page` при работе с Клиентами остаётся `maine`; внутреннее состояние хранится внутри владельца `MAINE`.

### Текущее состояние

Папки `clients` и `finance` не создаются заранее только ради структуры. Они появляются при фактической реализации соответствующих сущностей.

Особенно важно: **`clients.js` не создаётся автоматически.** Сначала проектируется сущность Клиента и определяется минимальный необходимый владелец логики. Не создавать файл только потому, что у Клиентов много функций.

## 13. ВЛАДЕНИЕ

Каждый верхнеуровневый MODULE является владельцем своего экрана и своей внутренней логики:

```text
JOURNAL   → Журнал
TIMETABLE → Календарь
MAINE     → Главная
CHAT      → Чат
SETTINGS  → Настройки
```

Вложенная функциональность остаётся внутри своего владельца и не выносится рядом с ним.

Другой MODULE не перехватывает DOM и не исправляет внутреннюю логику владельца обходным способом.

## 14. ЗАПРЕЩЕНО СОЗДАВАТЬ МУСОРНЫЕ СЛОИ

Не создавать без архитектурной необходимости:

```text
*-router-fix.js
*-navigation-fix.js
*-hours-fix.js
*-ui-fix.js
*-render.js
*-button.js
```

Не создавать:
- дублирующие render-функции для одного экрана;
- дополнительные обработчики click, конкурирующие с Core;
- локальные CSS;
- отдельные CSS для кнопок;
- верхнеуровневые MODULE для вложенных сущностей;
- временные файлы только для обхода проблемы.

Если что-то не работает, сначала найти фактического владельца и место, где действие, render или стиль определяется, затем исправлять первичный источник.

## 15. ПРОТОКОЛ РАБОТЫ

Перед изменением:

```text
1. Прочитать PROJECT_STATE.md
2. Проверить фактическое дерево проекта
3. Найти фактического владельца функции
4. Найти фактический источник действия
5. Найти фактический источник стиля
6. Изменить первичный источник
7. Проверить результат
8. Только после проверки создавать коммит
```

Нельзя считать задачу выполненной только потому, что код изменён.

Результат считается выполненным только после проверки фактического приложения/рендера.

## 16. ПРАВИЛО ДЛЯ СЛЕДУЮЩЕГО ЧАТА

Не добавлять новые JS/CSS/HTML-файлы по предположению.

Сначала определить:

```text
КТО владелец?
ЧТО именно должно работать?
ГДЕ находится первичный механизм?
НУЖЕН ЛИ вообще отдельный файл?
```

Если отдельный файл не нужен — не создавать его.

**Цель архитектуры CoBook: минимальное количество файлов, один Core, один CSS, единый механизм действий, единый механизм render и чёткое владение функциональностью.**
