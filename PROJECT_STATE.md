## Правило клиента и идентификаторов

В интерфейсе и рабочем разговоре сущность мастера называется **Клиент**.

`client_id` — единственный якорь клиента. Он всегда является **ровно четырёхзначным числом** в диапазоне `0000–9999`.

Допустимые примеры: `0000`, `0001`, `0014`, `0100`, `1000`, `3007`, `9999`.

Не создавать альтернативные формы `client_id` (`C_001`, `client_001`, `profile_id` и т.п.) для этой сущности.

`telegram_id` — идентификатор конкретного Telegram-аккаунта. Он не является `client_id` и не определяет автоматически нового клиента.

Один `client_id` может иметь несколько связанных Telegram ID:

`client_id → telegram_id + telegram_id + telegram_id ...`

Связь Telegram ID с клиентом выполняет мастер. Код не объединяет Telegram ID автоматически и не считает каждый Telegram ID отдельным клиентом после ручного объединения.

Цель связи — чтобы история и аналитика считали визиты по `client_id`, даже если один и тот же человек обращался через несколько Telegram ID.

Не вводить дополнительные идентификаторы клиента или отдельные сущности для этой задачи без прямого решения пользователя.

## SERVICE и SETTINGS

`SERVICE` — самостоятельный раздел, принадлежащий `SETTINGS`.

Структура:

`SETTINGS → SERVICE → PROCEDURES / PRODUCTS`

`SERVICE` не принадлежит `maine` и не принадлежит `management`.

`service-ui.js` не должен содержать функции `management()`/`maine()` или `clients()`. Он отвечает только за Сервис, Процедуры и Товары.

## LOYALTY

`LOYALTY` — самостоятельный раздел внутри `SETTINGS`.

Структура:

`SETTINGS → LOYALTY → PROGRAMS`

Лояльность не является частью `SERVICE`, `maine` или `management`.

Текущий функционал `LOYALTY`:

- открытие раздела Лояльность из Настроек;
- список сохранённых программ;
- создание программы;
- редактирование программы;
- удаление программы;
- сохранение программ в `localStorage` в ключе `cobook_loyalty_programs`.

Текущий конструктор программы содержит:

- название;
- условие по количеству посещений или сумме покупок;
- порог условия;
- награду: скидка в процентах, бесплатно или фиксированная цена;
- область применения: все клиенты или выбранные клиенты.

Это рабочая модель конструктора, но применение созданных программ к реальным записям/расчёту стоимости ещё не реализовано.

## Текущий реализованный функционал клиентов

`Главная → Клиенты` открывает самостоятельный экран списка.

Список хранится отдельно в `cobook_clients`.

Каждый клиент содержит:

- `client_id` — ровно 4 цифры;
- `name`;
- `telegram_ids[]` — список связанных Telegram ID.

Из списка открывается карточка конкретного `client_id`.

В карточке мастер может:

- изменить имя;
- добавить Telegram ID к существующему `client_id`;
- удалить ранее связанную связь Telegram ID.

Автоматического определения того, что два Telegram ID принадлежат одному человеку, нет.

Автоматического создания клиента по одному Telegram ID нет.

## Контекст адресации интерфейсов

Пользователь ставит задачу по принципу: **раздел → поле**. Техническая адресация зафиксирована в `UI_CONTEXT.md`.

- `График → календарь` = `SCHEDULE → CALENDAR`.
- `Журнал → месяц-календарь` = `JOURNAL → MONTH_CALENDAR`.
- `Всплывающий календарь` = `MODAL → DATE_PICKER`.

Если пользователь говорит только «календарь», после определения текущего рабочего раздела используется календарь этого раздела. Нельзя выбирать другой календарь по похожему имени CSS-класса или функции.

Перед изменением календаря обязательно определить его технический адрес и DOM-область. Перед удалением или заменой календарного файла/модуля обязательно проверить все подключения, вызовы, селекторы и зависимости по всему проекту.
