# CoBook — PROJECT STATE

## 1. ИСТОЧНИК ИСТИНЫ

`main` — текущая рабочая версия проекта.

Перед каждой задачей ChatGPT обязан:
1. прочитать актуальный `PROJECT_STATE.md` из `main`;
2. проверить фактическое дерево и код;
3. определить фактического владельца функции;
4. определить фактический источник действия;
5. определить фактический источник стиля;
6. только после этого вносить изменения.

Нельзя восстанавливать архитектуру по памяти и нельзя создавать файлы «на всякий случай».

## 2. БАЗОВАЯ СТРУКТУРА

```text
CoBook/
├── index.html              ← оболочка приложения
├── app.js                  ← только запуск
├── styles.css              ← ЕДИНЫЙ CSS всего приложения
└── app/
    ├── shared/
    │   └── core.js         ← центральная логика
    ├── journal/            ← Журнал
    ├── timetable/          ← Календарь
    ├── maine/               ← Главная
    ├── chat/                ← Чат
    └── settings/            ← Настройки
```

Вложенные папки принадлежат своему MODULE и не становятся отдельными верхнеуровневыми MODULE без архитектурной необходимости.

## 3. CORE — ЕДИНЫЙ ЦЕНТРАЛЬНЫЙ МЕХАНИЗМ

`app/shared/core.js` отвечает за:
- состояние приложения;
- навигацию;
- единый механизм render;
- приём пользовательских действий;
- маршрутизацию `data-action`;
- общие технические функции.

Модель кнопки:

```text
Кнопка
  ↓
data-action
  ↓
core.js
  ↓
центральная обработка
  ↓
владелец MODULE
```

MODULE не создаёт собственный глобальный обработчик `click`, если действие может быть обработано Core.

Запрещены конкурирующие обработчики, DOM-перехваты, `window.*`-мосты и временные fix-файлы для обхода Core.

## 4. ЕДИНЫЙ RENDER

Механизм render один — в `core.js`.

MODULE может иметь функцию `render()`, описывающую содержимое своего экрана. Это не отдельный renderer.

```text
core.js
  ↓
единый render-механизм
  ↓
render текущего владельца
  ↓
экран
```

Запрещено создавать независимые render-механизмы одного приложения.

## 5. ЕДИНЫЙ CSS

Во всём CoBook используется **только один CSS-файл**:

```text
styles.css
```

Он является единственным источником визуального стиля:
- кнопок;
- папок;
- полей;
- карточек;
- навигации;
- календаря;
- других UI-компонентов.

Запрещены локальные CSS внутри MODULE: `clients.css`, `finance.css`, `maine.css`, `settings.css`, `profile.css`, `service.css` и любые аналогичные файлы.

Новый уникальный визуальный элемент добавляется в общий `styles.css`.

### MAINE / Premium

В общем `styles.css` существует дополнительный визуальный вариант кнопок Главной:

```text
.premium-grid
.premium
```

Premium — часть общего `styles.css`, а не отдельный CSS-файл.

## 6. JS MODULE

JS не является обязательным для каждой папки.

JS создаётся только при наличии собственной логики: состояния, данных, формы, сохранения, динамического содержимого или действий владельца.

`app.js` — только запуск.

`core.js` — центральная обработка.

JS конкретного MODULE — только содержимое и логика этого MODULE.

Нельзя создавать `clients.js` или другой JS автоматически только потому, что существует папка/сущность.

SETTINGS

## 8. MAINE

```text
MAINE
├── Клиенты
└── Финансы
```

Клиенты и Финансы — внутренняя функциональность Main.

Клиенты физически находятся только внутри `app/maine/`.

Запрещены:
- `app/clients/`;
- `CoBook.modules.clients` как верхнеуровневый MODULE;
- создание `clients.js` только ради существования Клиентов.

Сначала проектируется сущность и её владелец, затем создаются только действительно необходимые файлы.

```text
*-router-fix.js
*-navigation-fix.js
*-hours-fix.js
*-ui-fix.js
*-render.js
*-button.js
```

Также запрещены:
- дублирующие render-механизмы;
- конкурирующие click/action-обработчики;
- локальные CSS;
- временные обходы;
- дублирование одного экрана в разных местах.

Если что-то не работает, сначала найти первичный источник проблемы, затем исправлять его. Не добавлять новый слой поверх ошибки.

Перед изменением:

```text

3. фактический владелец
4. фактический источник действия
5. фактический источник render
6. фактический источник стиля
7. изменение первичного источника
8. проверка
```

Нельзя считать задачу выполненной только потому, что код изменён.

## 12. ПОЛНЫЙ ПРОТОКОЛ ПРОВЕРКИ

Перед созданием финального commit обязательно:

1. проверить синтаксис всех JavaScript-файлов;
2. проверить загрузку скриптов и отсутствие JavaScript-ошибок;
3. проверить основные маршруты нижнего меню;
4. проверить переходы и возвраты затронутых разделов;
5. проверить основные действия изменённого MODULE;
6. проверить отсутствие регрессий;
7. проверить GitHub Pages deploy именно для того же commit SHA;
8. проверить фактически опубликованную версию приложения, а не только GitHub-файлы;
9. для интерактивных изменений проверить сценарий `нажатие → action → state → render → экран → возврат → повторное открытие`;
10. проверить повторные переходы;
11. проверить desktop и mobile;
12. при любой ошибке найти первопричину, исправить и повторить полный протокол.

**До успешного прохождения полного протокола запрещено создавать финальный commit или предоставлять пользователю ссылку на результат.**

## 13. ЖЁСТКОЕ ПРАВИЛО ОТВЕТА ЗАКАЗЧИКУ

Пользователь является заказчиком и не обязан работать с исходным кодом.

Запрещено присылать:
- исходный код вместо результата;
- diff вместо результата;
- GitHub-ссылку вместо приложения;
- непроверенную ссылку;
- commit вместо результата;
- инструкцию пользователю самостоятельно вставить код.

Если задача ещё не проверена, нельзя объявлять её завершённой. Работа продолжается до проверки либо задаётся только необходимый уточняющий вопрос.

## 14. ПРАВИЛО ДЛЯ СЛЕДУЮЩЕГО ЧАТА

Не добавлять файлы по предположению.

Перед созданием любого нового файла определить:

```text
КТО владелец?
ЧТО делает файл?
ЗАЧЕМ он нужен?
ГДЕ источник действия?
ГДЕ источник render?
ГДЕ источник стиля?
```

Если функцию уже обеспечивает `core.js` или `styles.css`, второй механизм не создавать.

Если файл не имеет подтверждённой роли — не создавать.

Если старый файл существует — сначала проверить его фактическое использование, а затем удалить или оставить на основании результата проверки.
