# CoBook — PROJECT STATE

## Источник истины

`main` — текущая рабочая и контрольная точка проекта.

## ОБЯЗАТЕЛЬНАЯ АРХИТЕКТУРА MODULE

CoBook строится как Mini App из самостоятельных MODULE. Каждый самостоятельный экран/раздел имеет собственную папку-владельца.

Целевая структура:

```text
CoBook/
├── app.js
└── app/
    ├── journal/
    ├── timetable/
    ├── maine/
    │   └── clients/
    ├── chat/
    ├── shared/
    └── settings/
        ├── settings.js
        ├── profile/
        │   ├── profile.js
        │   └── profile.css
        ├── service/
        │   ├── service.js
        │   ├── service.css
        │   ├── procedures/
        │   │   └── procedures.js
        │   └── products/
        │       └── products.js
        ├── documents/
        └── loyalty/
```

### КРИТИЧЕСКОЕ ПРАВИЛО ВЛАДЕНИЯ

`Clients` НЕ является самостоятельным MODULE верхнего уровня и НЕ является соседом `maine`.

Клиенты — функциональность `MAINE`, поэтому физически находятся только здесь:

```text
app/maine/clients/
```

Запрещено создавать или возвращать `app/clients/` и регистрировать `clients` как самостоятельный верхнеуровневый маршрут через `CoBook.modules.clients`.

Переход:

```text
Нижнее меню → Главная → Клиенты → список → карточка клиента
```

`state.page` для Клиентов остаётся `maine`. Вложенное состояние хранится внутри `maine`.

## app.js

`app.js` — только запуск приложения. Он не является владельцем функционала разделов.

## app/shared/core.js

`app/shared/core.js` содержит только общий технический механизм: состояние приложения, верхнеуровневую навигацию, маршрутизацию нижнего меню, общий `render`, обработку общих действий и общие утилиты.

`shared` не является владельцем бизнес-функциональности. В `shared` нельзя переносить код конкретного MODULE только ради удобства. Общий механизм выносится туда только если он действительно используется несколькими владельцами.

Если механизм потенциально используется несколькими разделами (например, работа со временем, датами или общими элементами UI), перед локальной реализацией необходимо определить его границу. Если из задачи это невозможно понять — сначала задать пользователю вопрос о назначении механизма. Не делать архитектурное предположение молча.

## MODULE ownership

Каждый верхнеуровневый MODULE является единственным владельцем своего экрана, действий, модальных окон, внутренней навигации, данных и локальных стилей. Вложенная функциональность хранится внутри папки владельца и не становится самостоятельным верхнеуровневым MODULE только из-за наличия собственных файлов.

Другой MODULE не изменяет внутреннюю реализацию владельца без необходимости, обусловленной общей архитектурой.

Запрещены:
- `*-router-fix.js`;
- `*-navigation-fix.js`;
- `*-hours-fix.js`;
- `*-ui-fix.js`;
- DOM-перехваты, созданные только для обхода архитектурной ошибки;
- дублирование одного `render`/экрана в нескольких местах;
- временные `window.*`-мосты между MODULE;
- реализация одного раздела одновременно в `app.js` и отдельном MODULE;
- вынесение вложенной функциональности в `app/` рядом с её владельцем;
- создание `app/clients/` для функциональности `MAINE → Клиенты`;
- регистрация `Clients` как `CoBook.modules.clients`.

Если проблема возникает в навигации, исправляется центральная маршрутизация или владелец MODULE, а не создаётся обход.

## Текущие границы

- `maine` — Главная мастера и владелец функциональности `Клиенты`.
- `maine/clients` — внутренняя реализация `MAINE → Клиенты`; не является верхнеуровневым MODULE.
- `SERVICE` — самостоятельный MODULE внутри `SETTINGS`.
- `SERVICE` является владельцем одного окна `Сервис` и его внутренних подразделов `Процедуры` и `Товары`.
- `app/settings/service/procedures/` и `app/settings/service/products/` — внутренние папки `SERVICE`, а не самостоятельные верхнеуровневые MODULE.
- В интерфейсе `SERVICE` кнопки `Процедуры` и `Товары` находятся одновременно сверху одного окна. Нажатие переключает содержимое нижней области того же окна, без перехода на отдельную страницу/модальное окно.
- `PROFILE` — самостоятельный MODULE внутри `SETTINGS`.
- `PROFILE` является владельцем профиля текущего пользователя CoBook: личной информации и профессиональной специализации.
- `app/settings/profile/` — физическое место `PROFILE`; не создавать `app/profile/`.
- `DOCUMENTS` — самостоятельный MODULE внутри `SETTINGS`.
- `LOYALTY` — самостоятельный MODULE внутри `SETTINGS`.
- `JOURNAL`, `TIMETABLE`, `MAINE`, `CHAT`, `SETTINGS` — MODULE нижней навигации.
- `SERVICE`, `PROFILE`, `DOCUMENTS`, `LOYALTY` не управляют другими MODULE.

## SERVICE: внутренние подразделы

Логическая структура:

```text
SETTINGS
└── SERVICE
    ├── ПРОЦЕДУРЫ
    └── ТОВАРЫ
```

Физическая структура:

```text
app/settings/service/
├── service.js
├── service.css
├── procedures/
│   └── procedures.js
└── products/
    └── products.js
```

`service.js` — владелец окна, переключателя и общего состояния `SERVICE`.

`procedures/procedures.js` — внутреннее представление и список процедур.

`products/products.js` — внутреннее представление и список товаров.

Оба подраздела используют одно окно `SERVICE`; они не регистрируются в `CoBook.modules` и не получают самостоятельный верхнеуровневый маршрут.

## PROFILE: профиль пользователя

Логическая структура:

```text
SETTINGS
└── PROFILE
    ├── Личные
    ├── Профессия
    └── Работа
```

Физическая структура:

```text
app/settings/profile/
├── profile.js
└── profile.css
```

`profile.js` — владелец экрана профиля, его формы, сохранения и локальных данных.

`Личные`:
- фото;
- имя (обязательное);
- телефон;
- О себе;
- Ссылки — отдельный внутренний список; Telegram подтягивается автоматически из регистрации, остальные ссылки добавляются через `+ Добавить ссылку`.
- Валюта НЕ относится к профилю, а принадлежит конкретному месту работы.

`Профессия`:
- профессия;
- опыт работы;
- О профессии.

`Работа` — массив мест работы. Каждое место работы является отдельной записью и содержит:
- название;
- город;
- адрес;
- рабочий телефон;
- график работы;
- валюта;
- рабочие ссылки;
- до 3 фото рабочего пространства;
- описание рабочего пространства.

Можно добавлять несколько мест работы, в том числе в разных городах и с разными валютами.

Профиль хранится локально в `cobook_profile` до появления отдельного серверного хранилища. Профиль не является профилем клиента и не связан с `client_id`.

## LOYALTY

`SETTINGS → LOYALTY` содержит независимые механизмы:
- `Программы`;
- `Сертификаты`;
- `Абонементы`;
- `Реферальная программа`;

Во всех подразделах и редакторах `LOYALTY` используется один общий `section-back-button` в `section-back-wrap`. Не создавать отдельные navigation/back DOM-фиксы.

## ОБЯЗАТЕЛЬНЫЙ ПРОТОКОЛ ЗАВЕРШЕНИЯ ЗАДАЧИ

Изменение считается завершённым только после полного цикла проверки.

Обязательно:
1. Проверить синтаксис **всех JavaScript-файлов проекта**, а не только изменённых файлов.
2. Проверить загрузку всех подключаемых скриптов и отсутствие ошибок JavaScript.
3. Проверить все основные маршруты нижнего меню.
4. Проверить переходы `SETTINGS → PROFILE / SERVICE / DOCUMENTS / LOYALTY` и возврат из подразделов.
5. Проверить основные действия изменённого MODULE.
6. Проверить отсутствие регрессий в затронутых связанных модулях.
7. Проверить, что GitHub Pages deploy успешно завершён **для того же commit SHA**, который содержит изменение.
8. Проверить фактическую опубликованную версию, а не только наличие файлов в GitHub.
9. Для интерактивных изменений проверить реальный сценарий: нажатие → изменение состояния → render → следующий экран → возврат → повторное открытие.
10. Для навигационных изменений отдельно проверить повторные переходы между всеми затронутыми разделами.
11. Проверить desktop и mobile сценарии. Работоспособность на одном устройстве не является доказательством готовности.
12. При обнаружении ошибки проверка считается проваленной; сначала исправить первопричину, затем повторить полный протокол.

Цель совместимости: iPhone/iPad, Android включая Huawei, macOS, Windows и современные мобильные/desktop-браузеры.

### ЖЁСТКИЙ ЗАПРЕТ НА ОТВЕТ ДО ЗАВЕРШЕНИЯ ЗАДАЧИ

Это правило относится не только к коммиту и ссылке, но и к **любому пользовательскому ответу, который останавливает текущую работу над поставленной задачей**.

Если пользователь поставил задачу на реализацию, ChatGPT обязан продолжать работу над ней до получения проверенного результата. До этого момента запрещено отправлять промежуточный ответ, который завершает текущий цикл работы, в том числе:

- сообщать, что задача готова, если она не прошла полный протокол проверки;
- выдавать коммит;
- выдавать ссылку на приложение;
- выдавать отчёт о частичной реализации;
- останавливаться после обнаружения проблемы и перекладывать продолжение на следующий ответ;
- отвечать объяснением вместо исправления, если исправление возможно без дополнительного вопроса.

Если проверка выявила ошибку, работа продолжается: **найти первопричину → исправить → повторить полный протокол проверки**. Непроверенный результат не считается результатом.

Исключение только одно: если для корректной реализации действительно отсутствует необходимое решение или требование пользователя неоднозначно и без ответа невозможно выбрать правильную архитектуру. Тогда допускается один необходимый уточняющий вопрос. До получения ответа пользователя никаких коммитов по незавершённой задаче не делать.
