## Архитектурная граница текущего продукта

Сейчас разрабатывается только лёгкий `CoBook Master` для одного мастера.

Внешняя система, которая создаёт/подключает экземпляры мастеров, находится за пределами этого Mini App.

Внутри текущего продукта учитываются только источники данных:

- `manual` — данные введены мастером;
- `api` — данные переданы внешней системой через API.

Административная логика салонов, сотрудников, кабинетов, кресел, коворкингов и других бизнес-ресурсов в текущий `CoBook Master` не переносится.

## Правило сущностей и идентификаторов

Базовая сущность человека — `PROFILE`.

До назначения отношения с мастером профиль не называется клиентом.

- `profile_id` — постоянный внутренний идентификатор профиля;
- `master_id` — идентификатор мастера;
- `procedure_id` — идентификатор процедуры;
- `product_id` — идентификатор товара;
- `booking_id` — идентификатор записи;
- `location_id` — идентификатор места работы;
- `document_id` — идентификатор документа.

Телефон, Telegram ID и внешний API ID не являются `profile_id`. Это точки идентификации/входа, позволяющие найти соответствующий `PROFILE`.

`CLIENT` — не самостоятельный тип человека. Это отношение `MASTER ↔ PROFILE`.

Будущая базовая цепочка записи:

`PROFILE → CLIENT relation → BOOKING → PROCEDURE + LOCATION + DATE/TIME`.

Не использовать `client_id` как идентификатор самого человека, если для этого достаточно `profile_id`.

## Текущий этап разработки

Перед карточкой клиента выполняется ревизия и нормализация сущностей и связей.

Порядок текущего этапа:

1. `PROFILE` и идентификация профиля;
2. `MASTER` и профиль мастера;
3. `LOCATION`;
4. связь `MASTER ↔ PROFILE` для клиента;
5. `PROCEDURE`;
6. `BOOKING`;
7. только после этого — полноценная карточка клиента и связь `CLIENT → PROCEDURE → DATE/TIME → BOOKING`.

Карточка клиента пока не реализуется как следующий шаг, пока модель сущностей и идентификаторов не согласована.

## Контекст адресации интерфейсов

Пользователь ставит задачу по принципу: **раздел → поле**. Техническая адресация зафиксирована в `UI_CONTEXT.md`.

- `График → календарь` = `SCHEDULE → CALENDAR`.
- `Журнал → месяц-календарь` = `JOURNAL → MONTH_CALENDAR`.
- `Всплывающий календарь` = `MODAL → DATE_PICKER`.

Если пользователь говорит только «календарь», после определения текущего рабочего раздела используется календарь этого раздела. Нельзя выбирать другой календарь по похожему имени CSS-класса или функции.

Перед изменением календаря обязательно определить его технический адрес и DOM-область. Перед удалением или заменой календарного файла/модуля обязательно проверить все подключения, вызовы, селекторы и зависимости по всему проекту.

## Правило рабочих изменений

Вся разработка и все рабочие изменения выполняются непосредственно в `main`.

Другие ветки не создавать без необходимости. Если возникает необходимость создать новую ветку, она создаётся **только после трёх отдельных подтверждений пользователя, в каждом из которых он прямо пишет: «создаем новую ветку»**. До третьего такого подтверждения ветку не создавать.

`main` является единственной рабочей и контрольной точкой проекта, если пользователь явно не распорядился иначе.
