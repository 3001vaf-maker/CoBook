# CoBook — PROJECT STATE

## Источник истины

`main` — текущая рабочая и контрольная точка проекта.

## ОБЯЗАТЕЛЬНАЯ АРХИТЕКТУРА MODULE

CoBook строится как Mini App из самостоятельных MODULE. Каждый самостоятельный экран/раздел имеет собственную папку-владельца.

Целевая структура:

```text
CoBook/
├── app.js
└── app/
    ├── journal/
    ├── timetable/
    ├── maine/
    │   └── clients/
    ├── chat/
    ├── shared/
    └── settings/
        ├── settings.js
        ├── profile/
        │   ├── profile.js
        │   └── profile.css
        ├── service/
        │   ├── service.js
        │   ├── service.css
        │   ├── procedures/
        │   │   └── procedures.js
        │   └── products/
        │       └── products.js
        ├── documents/
        └── loyalty/
```

### КРИТИЧЕСКОЕ ПРАВИЛО ВЛАДЕНИЯ

`Clients` НЕ является самостоятельным MODULE верхнего уровня и НЕ является соседом `maine`.

Клиенты — функциональность `MAINE`, поэтому физически находятся только здесь:

```text
app/maine/clients/
```

Запрещено создавать или возвращать `app/clients/` и регистрировать `clients` как самостоятельный верхнеуровневый маршрут через `CoBook.modules.clients`.

Переход:

```text
Нижнее меню → Главная → Клиенты → список → карточка клиента
```

`state.page` для Клиентов остаётся `maine`. Вложенное состояние хранится внутри `maine`.

## app.js

`app.js` — только запуск приложения. Он не является владельцем функционала разделов.

## app/shared/core.js

`app/shared/core.js` содержит только общий технический механизм: состояние приложения, верхнеуровневую навигацию, маршрутизацию нижнего меню, общий `render`, обработку общих действий и общие утилиты.

`shared` не является владельцем бизнес-функциональности. В `shared` нельзя переносить код конкретного MODULE только ради удобства. Общий механизм выносится туда только если он действительно используется несколькими владельцами.

Если механизм потенциально используется несколькими разделами (например, работа со временем, датами или общими элементами UI), перед локальной реализацией необходимо определить его границу. Если из задачи это невозможно понять — сначала задать пользователю вопрос о назначении механизма. Не делать архитектурное предположение молча.

## MODULE ownership

Каждый верхнеуровневый MODULE является единственным владельцем своего экрана, действий, модальных окон, внутренней навигации, данных и локальных стилей. Вложенная функциональность хранится внутри папки владельца и не становится самостоятельным верхнеуровневым MODULE только из-за наличия собственных файлов.

Другой MODULE не изменяет внутреннюю реализацию владельца без необходимости, обусловленной общей архитектурой.

Запрещены:
- `*-router-fix.js`;
- `*-navigation-fix.js`;
- `*-hours-fix.js`;
- `*-ui-fix.js`;
- DOM-перехваты, созданные только для обхода архитектурной ошибки;
- дублирование одного `render`/экрана в нескольких местах;
- временные `window.*`-мосты между MODULE;
- реализация одного раздела одновременно в `app.js` и отдельном MODULE;
- вынесение вложенной функциональности в `app/` рядом с её владельцем;
- создание `app/clients/` для функциональности `MAINE → Клиенты`;
- регистрация `Clients` как `CoBook.modules.clients`.

Если проблема возникает в навигации, исправляется центральная маршрутизация или владелец MODULE, а не создаётся обход.

## Текущие границы

- `maine` — Главная мастера и владелец функциональности `Клиенты`.
- `maine/clients` — внутренняя реализация `MAINE → Клиенты`; не является верхнеуровневым MODULE.
- `SERVICE` — самостоятельный MODULE внутри `SETTINGS`.
- `SERVICE` является владельцем одного окна `Сервис` и его внутренних подразделов `Процедуры` и `Товары`.
- `app/settings/service/procedures/` и `app/settings/service/products/` — внутренние папки `SERVICE`, а не самостоятельные верхнеуровневые MODULE.
- В интерфейсе `SERVICE` кнопки `Процедуры` и `Товары` находятся одновременно сверху одного окна. Нажатие переключает содержимое нижней области того же окна, без перехода на отдельную страницу/модальное окно.
- `PROFILE` — самостоятельный MODULE внутри `SETTINGS`.
- `PROFILE` является владельцем профиля текущего пользователя CoBook: личной информации и профессиональной специализации.
- `app/settings/profile/` — физическое место `PROFILE`; не создавать `app/profile/`.
- `DOCUMENTS` — самостоятельный MODULE внутри `SETTINGS`.
- `LOYALTY` — самостоятельный MODULE внутри `SETTINGS`.
- `JOURNAL`, `TIMETABLE`, `MAINE`, `CHAT`, `SETTINGS` — MODULE нижней навигации.
- `SERVICE`, `PROFILE`, `DOCUMENTS`, `LOYALTY` не управляют другими MODULE.

## SERVICE: внутренние подразделы

Логическая структура:

```text
SETTINGS
└── SERVICE
    ├── ПРОЦЕДУРЫ
    └── ТОВАРЫ
```

Физическая структура:

```text
app/settings/service/
├── service.js
├── service.css
├── procedures/
│   └── procedures.js
└── products/
    └── products.js
```

`service.js` — владелец окна, переключателя и общего состояния `SERVICE`.

`procedures/procedures.js` — внутреннее представление и список процедур.

`products/products.js` — внутреннее представление и список товаров.

Оба подраздела используют одно окно `SERVICE`; они не регистрируются в `CoBook.modules` и не получают самостоятельный верхнеуровневый маршрут.

## PROFILE: профиль пользователя

Логическая структура:

```text
SETTINGS
└── PROFILE
    ├── Личная информация
    └── Профессиональная информация
```

Физическая структура:

```text
app/settings/profile/
├── profile.js
└── profile.css
```

`profile.js` — владелец экрана профиля, его формы, сохранения и локальных данных.

Профиль предназначен для бьюти-пользователей CoBook. В форме предусмотрены:
- имя;
- телефон;
- email;
- дата рождения;
- город;
- специализация `Кто я`;
- опыт работы;
- краткая информация `О себе`.

`Кто я` заполняется выбором из списка бьюти-специализаций: парикмахер, барбер, колорист, мастер по наращиванию волос, мастер маникюра, мастер педикюра, нейл-мастер, визажист, бровист, лэшмейкер, косметолог, эстетист, мастер депиляции, мастер шугаринга, мастер перманентного макияжа, массажист, стилист/имиджмейкер, тату-мастер и `Другое`.

Профиль хранится локально в `cobook_profile` до появления отдельного серверного хранилища.

Профиль не является профилем клиента и не связан с `client_id`.

## LOYALTY

`SETTINGS → LOYALTY` содержит независимые механизмы:
- `Программы` — условия и награды: скидка %, бесплатно (процедура или ручной подарок), деньги;
- `Сертификаты` — отдельный предоплаченный номинал и баланс;
- `Абонементы` — пакет предоплаченных посещений/услуг;
- `Реферальная программа` — денежное или процентное вознаграждение;
- `Личный счёт` — денежный баланс с начислениями и списаниями;
- `Депозиты` — предоплаченная программа с фиксированным взносом, скидкой и периодом действия.

### Навигация LOYALTY

Во всех подразделах и редакторах `LOYALTY` используется один общий элемент `section-back-button`.

- текст кнопки всегда `Назад`;
- кнопка находится в едином нижнем контейнере `section-back-wrap` непосредственно перед основной нижней навигацией приложения;
- из подраздела кнопка возвращает на главный экран `LOYALTY`;
- из главного экрана `LOYALTY` тот же элемент возвращает в `SETTINGS`;
- не создавать отдельные `loyalty-navigation`, `loyalty-back` или DOM-фиксы для отдельных экранов.

## ОБЯЗАТЕЛЬНЫЙ ПРОТОКОЛ ЗАВЕРШЕНИЯ ЗАДАЧИ

Изменение считается завершённым только после полного цикла проверки.

Обязательно:
1. Проверить синтаксис **всех JavaScript-файлов проекта**, а не только изменённых файлов.
2. Проверить загрузку всех подключаемых скриптов и отсутствие ошибок JavaScript.
3. Проверить все основные маршруты нижнего меню.
4. Проверить переходы `SETTINGS → PROFILE / SERVICE / DOCUMENTS / LOYALTY` и возврат из подразделов.
5. Проверить основные действия изменённого MODULE.
6. Проверить отсутствие регрессий в затронутых связанных модулях.
7. Проверить, что GitHub Pages deploy успешно завершён **для того же commit SHA**, который содержит изменение.
8. Только после успешного завершения всех проверок разрешено считать задачу рабочей.

Для `SERVICE` дополнительно проверить:
- открытие `SETTINGS → SERVICE`;
- одновременное наличие кнопок `Процедуры` и `Товары`;
- переключение `Процедуры → Товары` без смены страницы;
- переключение `Товары → Процедуры` без смены страницы;
- отображение списка и кнопки добавления в каждом подразделе;
- добавление, редактирование и удаление процедуры;
- добавление, редактирование и удаление товара;
- возврат из `SERVICE` в `SETTINGS`.

Для `PROFILE` дополнительно проверить:
- открытие `SETTINGS → PROFILE`;
- отображение всех полей профиля;
- выбор специализации из списка `Кто я`;
- выбор опыта работы;
- сохранение и повторное отображение данных;
- возврат из `PROFILE` в `SETTINGS`.

### КРОСС-ПЛАТФОРМЕННОЕ ТРЕБОВАНИЕ

CoBook должен работать как единое веб-приложение независимо от устройства и браузера пользователя. Нельзя считать задачу завершённой только потому, что изменение работает на одном конкретном устройстве.

Поддерживаемая цель:
- iPhone / iPad;
- Android, включая устройства Huawei;
- macOS;
- Windows;
- современные мобильные и desktop-браузеры.

Нельзя использовать устройство, ОС, touch-события или конкретный браузер как неявное обязательное условие для работы основной функциональности. Если различие поведения обнаружено между платформами, причина должна быть найдена и исправлена в общем коде приложения, а не обходиться отдельным платформенным костылём.

Для изменений, затрагивающих интерактивность, формы, навигацию или загрузку MODULE, обязательно учитывать совместимость desktop и mobile браузеров. Поведение на iPhone не является доказательством готовности для Mac/Windows/Android, и наоборот.

### ПРОТОКОЛ ДОСТАВКИ И АКТУАЛЬНОСТИ ASSETS

Публикация кода в GitHub и успешный GitHub Pages deploy сами по себе не считаются доказательством, что пользователь видит новую версию приложения.

Для каждого изменения, затрагивающего HTML/JS/CSS или порядок загрузки MODULE, обязательно:
1. Убедиться, что изменённые файлы подключаются из актуального `main`.
2. Проверить, что опубликованный GitHub Pages deploy относится к **тому же commit SHA**, который содержит изменение.
3. Использовать cache-busting для изменяемых JS/CSS-ассетов, если приложение может получить старую копию из браузерного кэша.
4. После deploy проверить опубликованный маршрут/экран и фактическое наличие изменённого элемента или поведения, а не только наличие файла в репозитории.
5. Если опубликованная версия не подтверждается — задача считается незавершённой; новый коммит для отчёта пользователю не выдаётся до исправления и повторной проверки.

Cache-busting должен быть частью общего механизма загрузки ассетов, а не набором локальных ручных исправлений отдельных MODULE.

**Нельзя отправлять пользователю сообщение о завершённой разработке, коммите или ссылке на приложение, если результат ещё не прошёл полный обязательный протокол проверки.**

Если проверка не завершена, упала или результат нельзя подтвердить как рабочий — **не формировать промежуточный пользовательский отчёт о готовности и не выдавать ссылку на непроверенное приложение**. Сначала исправить проблему, повторить проверки и только после успешного результата ответить пользователю.
