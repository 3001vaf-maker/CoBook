# CoBook — PROJECT STATE

## Источник истины

`main` — текущая рабочая и контрольная точка проекта.

## ОБЯЗАТЕЛЬНАЯ АРХИТЕКТУРА MODULE

CoBook строится как Mini App из самостоятельных MODULE. Каждый самостоятельный экран/раздел имеет собственную папку-владельца.

Целевая структура:

```text
CoBook/
├── app.js
└── app/
    ├── journal/
    ├── timetable/
    ├── maine/
    │   └── clients/
    ├── chat/
    ├── shared/
    └── settings/
        ├── settings.js
        ├── service/
        ├── documents/
        └── loyalty/
```

### КРИТИЧЕСКОЕ ПРАВИЛО ВЛАДЕНИЯ

`Clients` НЕ является самостоятельным MODULE верхнего уровня и НЕ является соседом `maine`.

Клиенты — функциональность `MAINE`, поэтому физически находятся только здесь:

```text
app/maine/clients/
```

Запрещено создавать или возвращать `app/clients/` и регистрировать `clients` как самостоятельный верхнеуровневый маршрут через `CoBook.modules.clients`.

Переход:

```text
Нижнее меню → Главная → Клиенты → список → карточка клиента
```

`state.page` для Клиентов остаётся `maine`. Вложенное состояние хранится внутри `maine`.

## app.js

`app.js` — только запуск приложения. Он не является владельцем функционала разделов.

## app/shared/core.js

`app/shared/core.js` содержит только общий технический механизм: состояние приложения, верхнеуровневую навигацию, маршрутизацию нижнего меню, общий `render`, обработку общих действий и общие утилиты.

`shared` не является владельцем бизнес-функциональности. В `shared` нельзя переносить код конкретного MODULE только ради удобства. Общий механизм выносится туда только если он действительно используется несколькими владельцами.

Если механизм потенциально используется несколькими разделами (например, работа со временем, датами или общими элементами UI), перед локальной реализацией необходимо определить его границу. Если из задачи это невозможно понять — сначала задать пользователю вопрос о назначении механизма. Не делать архитектурное предположение молча.

## MODULE ownership

Каждый верхнеуровневый MODULE является единственным владельцем своего экрана, действий, модальных окон, внутренней навигации, данных и локальных стилей. Вложенная функциональность хранится внутри папки владельца и не становится самостоятельным верхнеуровневым MODULE только из-за наличия собственных файлов.

Другой MODULE не изменяет внутреннюю реализацию владельца без необходимости, обусловленной общей архитектурой.

Запрещены:
- `*-router-fix.js`;
- `*-navigation-fix.js`;
- `*-hours-fix.js`;
- `*-ui-fix.js`;
- DOM-перехваты, созданные только для обхода архитектурной ошибки;
- дублирование одного `render`/экрана в нескольких местах;
- временные `window.*`-мосты между MODULE;
- реализация одного раздела одновременно в `app.js` и отдельном MODULE;
- вынесение вложенной функциональности в `app/` рядом с её владельцем;
- создание `app/clients/` для функциональности `MAINE → Клиенты`;
- регистрация `Clients` как `CoBook.modules.clients`.

Если проблема возникает в навигации, исправляется центральная маршрутизация или владелец MODULE, а не создаётся обход.

## Текущие границы

- `maine` — Главная мастера и владелец функциональности `Клиенты`.
- `maine/clients` — внутренняя реализация `MAINE → Клиенты`; не является верхнеуровневым MODULE.
- `SERVICE` — самостоятельный MODULE внутри `SETTINGS`: `SETTINGS → SERVICE → PROCEDURES / PRODUCTS`.
- `DOCUMENTS` — самостоятельный MODULE внутри `SETTINGS`.
- `LOYALTY` — самостоятельный MODULE внутри `SETTINGS`.
- `JOURNAL`, `TIMETABLE`, `MAINE`, `CHAT`, `SETTINGS` — MODULE нижней навигации.
- `SERVICE`, `DOCUMENTS`, `LOYALTY` не управляют другими MODULE.

## Клиенты и идентификаторы

В интерфейсе рабочая сущность мастера называется **Клиент**.

`client_id` — единственный якорь клиента и всегда ровно четырёхзначное число `0000–9999`.

`telegram_id` — идентификатор конкретного Telegram-аккаунта. Он не является `client_id` и автоматически не создаёт нового клиента.

Один `client_id` может иметь несколько связанных Telegram ID. Связь выполняет мастер.

Не вводить альтернативные идентификаторы без прямого решения пользователя.

## LOYALTY

`SETTINGS → LOYALTY` содержит независимые механизмы:
- `Программы` — условия и награды: скидка %, бесплатно (процедура или ручной подарок), деньги;
- `Сертификаты` — отдельный предоплаченный номинал и баланс;
- `Абонементы` — пакет предоплаченных посещений/услуг;
- `Реферальная программа` — денежное или процентное вознаграждение;
- `Личный счёт` — денежный баланс с начислениями и списаниями;
- `Депозиты` — предоплаченная программа с фиксированным взносом, скидкой и периодом действия.

### Навигация LOYALTY

Во всех подразделах и редакторах `LOYALTY` используется один общий элемент `section-back-button`.

- текст кнопки всегда `Назад`;
- кнопка находится в едином нижнем контейнере `section-back-wrap` непосредственно перед основной нижней навигацией приложения;
- из подраздела кнопка возвращает на главный экран `LOYALTY`;
- из главного экрана `LOYALTY` тот же элемент возвращает в `SETTINGS`;
- не создавать отдельные `loyalty-navigation`, `loyalty-back` или DOM-фиксы для отдельных экранов.

## ОБЯЗАТЕЛЬНЫЙ ПРОТОКОЛ ЗАВЕРШЕНИЯ ЗАДАЧИ

Изменение считается завершённым только после полного цикла проверки.

Обязательно:
1. Проверить синтаксис **всех JavaScript-файлов проекта**, а не только изменённых файлов.
2. Проверить загрузку всех подключаемых скриптов и отсутствие ошибок JavaScript.
3. Проверить все основные маршруты нижнего меню.
4. Проверить переходы `SETTINGS → SERVICE / DOCUMENTS / LOYALTY` и возврат из подразделов.
5. Проверить основные действия изменённого MODULE.
6. Проверить отсутствие регрессий в затронутых связанных модулях.
7. Проверить, что GitHub Pages deploy успешно завершён **для того же commit SHA**, который содержит изменение.
8. Только после успешного завершения всех проверок разрешено считать задачу рабочей.

### ЖЁСТКИЙ ЗАПРЕТ НА ПРЕЖДЕВРЕМЕННЫЙ ОТВЕТ

**Нельзя отправлять пользователю сообщение о завершённой разработке, коммите или ссылке на приложение, если результат ещё не прошёл полный обязательный протокол проверки.**

Если проверка не завершена, упала или результат нельзя подтвердить как рабочий — **не формировать промежуточный пользовательский отчёт о готовности и не выдавать ссылку на непроверенное приложение**. Сначала исправить проблему, повторить проверки и только после успешного результата ответить пользователю.

Нельзя писать пользователю: «готово», «изменения произведены», «коммит», «деплой», «ссылка для проверки» или аналогичный отчёт до успешного завершения проверки.

### Формат единственного ответа после успешной проверки

```text
Изменения произведены и проверены.

Коммит: <полный SHA>

```

Без дополнительных объяснений, если пользователь их не запросил.

## Архитектурная проверка MAINE → Клиенты

Дополнительно обязательно проверять:
- `app/clients/` отсутствует;
- существует `app/maine/clients/`;
- в `index.html` загружаются только `app/maine/clients/*`;
- `CoBook.modules.clients` отсутствует;
- `state.page` при открытии Клиентов остаётся `maine`;
- `Главная → Клиенты → список → карточка клиента → обратно` работает внутри владельца `maine`;
- переход в любой пункт нижнего меню сбрасывает вложенное состояние `maine`.

Визуальный рендер без работающего действия не считается реализацией.

## Правила разработки

1. Работать непосредственно в `main`.
2. Перед изменением читать этот `PROJECT_STATE.md` из текущего `main`.
3. Не менять архитектурные границы без решения пользователя.
4. Не выдавать визуальный рендер за реализованный функционал.
5. Не объявлять изменение рабочим, пока полный протокол проверки не завершён успешно.
6. Не создавать обходные фиксы вместо исправления владельца MODULE или центрального маршрута.
7. Изменение одного MODULE не должно менять другой MODULE без явной архитектурной необходимости.
8. Перед коммитом проверять приложение целиком.
9. После успешной проверки в ответе по завершённой задаче указывать полный SHA коммита и рабочую ссылку на Mini App.
10. Перед созданием нового верхнеуровневого каталога в `app/` проверять, является ли его функциональность самостоятельным пунктом нижней навигации. Если нет — размещать её внутри папки фактического владельца.
11. Если назначение механизма неясно и от него зависит архитектурная граница — сначала задать пользователю вопрос. До ответа пользователя код не менять и коммит не создавать.
